## 1. User outcome and scope
Jonathan can ask an agent to join using a named template, such as "adversarial reviewer". The skill resolves that explicit selection, loads only that template, and joins with a recorded binding. Existing joins without a template behave exactly as today. A template adds task/role guidance through the skill; it cannot rewrite a host system prompt, permissions, project controls or Jonathan's instructions.
Ship a small agreed built-in catalog. Proposed first four: conservative-engineer, creative-designer, adversarial-reviewer, defensive-reviewer. The candidate analysis below compares broader options; catalog selection awaits Jonathan. General-engineer/general-reviewer are optional baseline ideas, not assumed value-added presets. One optional selection per project agent UUID. Keep the existing free-text role independent and unchanged; no inferred template from role, handle, provider or project goal.
Out of v1: switching an existing identity's template, stacking, custom/project-local overrides, template editors and behavior enforcement. Jonathan explicitly deferred switching; separate resolution/binding helpers allow adding it later without changing IDs or folding selection into role.

## 2. Files and discovery
Keep the portable Vibeguild skill. Add references/templates.md as the small catalog/selection procedure and references/templates/<slug>.md for the selected bodies. The main SKILL.md gets a short conditional link: read the selection reference only when a template is explicitly requested or restoring this identity's existing selection. Do not embed all bodies in SKILL.md, general_context, roster, broadcasts or ordinary bootstrap. Installed references/templates copies are documentation for humans only; agents obtain a new body from the coordinator and subsequently restore only their verified own snapshot, never by loading the installed markdown body.
A small app resolver (proposed vibeguild/templates.py) owns a fixed built-in allowlist, titles, relative source paths and selected-content digest calculation. Listing metadata does not read template bodies. Bound the v1 metadata catalog to 32 entries and 16 KiB serialized UTF-8 total, with short id/title/summary fields; reject an oversized catalog clearly rather than silently truncating it. Resolving a selected template reads only that body. Accept canonical slugs; the skill maps natural-language display names through the catalog. Unknown/ambiguous names must not silently choose another template. Reject path syntax/traversal; no arbitrary file loading.
Project-local/custom sources are a scope deferral. Future explicit sources can be added behind the resolver with distinct provenance; no lookup precedence is implemented or promised in v1.
install-skill already copies the entire skill tree; document and verify that templates are included. Do not rewrite users' global installed skill copies automatically.

## 3. Coordinator binding and the actual client
The installed skill scripts/vibeguild_client.py is a thin launcher into vibeguild.cli through its app.json pointer; it is not a second CLI implementation. Add flags/read helpers in vibeguild/cli.py so the launcher, vibeguild command and python -m vibeguild share behavior.
Add optional join --template <slug>. The coordinator resolves the selected slug from its own package copy and persists optional template_ref {id, sha256} separately from role. Register returns that binding. No client-computed expected digest or pre-join body handshake is required. Direct HTTP registration uses the same resolver/validation. Unknown names fail before any identity is created. Registration retry IDs return the same identity/result.
Missing/null template_ref means no selection. Existing projects and joins remain untemplated: no inference, migration default or backfill. Expose metadata only in join/resume results, this agent's bootstrap identity, roster and generated recovery. Do not add a setter/switch operation in v1. A small binding helper leaves that future operation localized.
Use SHA-256 of canonical UTF-8 body bytes (LF line endings, no BOM) consistently for registration, explicit reads and saved-copy verification. Validate format and bound the selected body to a documented small size (proposed 16 KiB) so a template cannot overwhelm bootstrap or the explicit read response.
The coordinator's package is authoritative for current shipped bodies. A binding describes the chosen version; it is not proof the model read or obeyed it.

## 4. Explicit read and verified recovery
Add one loopback read endpoint for built-in template metadata and explicit selected-body retrieval. A credential-free GET is intentional because built-ins are public, project-independent package text and discovery can precede joining; retain existing Host/Origin/Sec-Fetch checks. It must never expose credentials, arbitrary paths, agent memory or project-local files. List mode returns metadata only; explicit show mode reads and returns only the requested body and digest. No automatic body in join or bootstrap.
Shared CLI contract: templates lists metadata; templates --show <slug> retrieves the explicit body+digest from the coordinator. A --save mode requires the project/agent/session identity, obtains that identity's binding and memory_folder from an authenticated coordinator read, and derives exactly memory/template.md within that agent directory; no arbitrary destination argument. Normalize/hash the received body, compare with the recorded binding, and write atomically only on a match. Verify resolved containment and reject a destination resolving outside the returned agent directory, including symlink/junction escapes. These are post-read verification options, not a join handshake. Use a helper shared by the actual save/read path and its tests; do not rely on model-authored hashing scripts or duplicated test logic. An existing-snapshot verification/read helper uses the same canonicalization and containment checks without requiring a current-package body match; otherwise a valid old snapshot could not survive an upgrade. These shared CLI helpers are exercised by the recovery tests. Paths come from authenticated identity metadata, never template text or another agent's requested UUID.
Skill sequence: explicit request -> resolve catalog name -> join with slug -> receive template_ref -> show the selected body -> verify against template_ref and save atomically as memory/template.md -> read/follow it -> link from MEMORY.md -> checkpoint. Do this before template-specific work. If the project is paused, checkpoint/monitor controls and defer new template loading/saving and template-specific work until permitted. This intentionally preserves the existing skill pause contract; a public read capability does not imply permission to carry out a paused assignment. A dormant profile's owner-selected binding follows the same loading procedure on its first resume.
On resume/context recovery of the same UUID, the original opt-in remains valid. Verify/read only its own saved snapshot against template_ref. A current-package change does not invalidate a matching saved snapshot and must not silently replace it. If the copy is absent, request the coordinator's selected body and save only if the recorded digest matches. Missing content, write failure or mismatch is explicit: checkpoint the problem, request a matching copy or Jonathan's direction, and continue ordinary control monitoring. Never silently follow a different version.
The coordinator persists binding metadata only, not body text in the journal or shared context. The explicitly opened human profile may retrieve the exact bound instructions through the owner-only read described below; that exception does not add bodies to agent projections. Generated recovery includes the binding, own snapshot path and the verification procedure. Existing agent-owned memory files are not overwritten by ordinary recovery projection. Future explicit switching can update a binding and its snapshot without changing the free-text role or identity.

## 6. Useful specializations and candidate catalog
Jonathan's additional request 1cb32751-0877-4475-8df4-6dc773e26367 sets a higher bar than generic role labels. A template earns its place by changing attention, work order or an explicit tradeoff and producing an artifact useful to the team. Name its usual phase and primary artifact; roles sharing both are candidates for merging. Phases describe useful application, not a mandatory automated pipeline. "Think logically", "be creative" and "write good code" are insufficient. Templates specialize existing capability; they do not claim to increase underlying model intelligence.

| Candidate | Usual phase | Primary artifact | Distinct workflow and output | Where its bias must yield |
|---|---|---|---|---|
| Conservative patch engineer | Implementation | Minimal complete patch + regression evidence | Identify required behavior and preserved invariants; find the smallest complete intervention using existing mechanisms; justify changed boundaries and exclude unrelated cleanup. Deliver focused diff + regression evidence. | Minimize disruption, not literal line count. Reject tiny brittle workarounds; do not obstruct an explicitly requested redesign. |
| Creative solution designer | Before design convergence | Distinct approaches + chosen option/experiment | Explore materially different mechanisms under real constraints, including a negotiable assumption; reduce the central uncertainty with a cheap sketch/example/experiment and recommend a concrete option. | Time-box exploration. No cosmetic alternative lists, novelty for its own sake or unsolicited implementation. |
| Adversarial design reviewer | Plan/design review | Premise challenge or justified acceptance | Extract the strongest claims, seek concrete counterexamples and compare an alternative under the same criteria. Deliver an evidenced challenge or explain why the design survives it. | Challenge ideas, not people. No manufactured objections, veto of the requested product or unrelated scope expansion. |
| Defensive regression reviewer | Diff review | Compatibility/risk map + reproduced findings | Trace existing caller/user expectations and changed failure/boundary paths; reproduce likely breakage and investigate meaningful coverage gaps. Deliver risk/compatibility map + specific regression checks. | Risk-based, not an exhaustive unrelated audit. No blanket coverage demands or unmeasured performance claims. |
| Failure investigator | Incident diagnosis | Causal explanation + discriminating evidence | Maintain competing falsifiable hypotheses; choose discriminating observations; reduce to a reproduction and separate cause from symptom. Deliver causal evidence and a regression strategy. | Overkill for an understood trivial fix. Stop investigating once evidence is decisive; patch only if assigned. |
| Contract/integration reviewer | Integration or migration review | Producer/consumer contract result | Map producer/consumer assumptions, lifecycle/version changes and interactions across parallel patches; exercise real seams. Deliver broken-contract evidence or a bounded compatibility result and migration impact. | Avoid rereviewing every line; can merge into defensive review for a small monolith. |
| Test challenger | Verification review | Demonstrated blind spot + detecting test | Seek vacuous assertions, mirrored assumptions and untested real entry points; demonstrate a blind spot with an authorized counterexample or sensitivity check. Deliver a test that catches the defect. | No coverage-percentage chase or mutations in shared work. Can be a focused defensive-review assignment rather than another permanent role. |
| Performance investigator | Performance diagnosis/validation | Comparable measurements + bottleneck analysis | Establish workload/baseline, localize a measured bottleneck, compare the same workload after the candidate change. Deliver measurements and uncertainty/limitations. | No speculative optimization. If measurement is unavailable, state that; not a default role for every feature. |
| User-workflow critic | Interaction design or acceptance | Observed friction + focused alternative | Walk the user's path through entry, interruption, failure and recovery; distinguish observed friction from heuristic predictions. Deliver reproducible friction and a focused interaction alternative. | Respect the product brief; no unsolicited visual redesign or claim of browser observation without actually using one. |

## 7. Verification and acceptance
Mechanics:
- Real CLI selected-template round trip into register -> state -> roster -> resume -> bootstrap -> generated recovery. Direct HTTP registration obeys the same validation.
- No-template joins and legacy reload/resume retain existing behavior and never load a template body.
- Resolver rejects unknown IDs/paths, loads only the chosen body, and catalog listing and automatic UI/peer/bootstrap output contain metadata only; only explicit selected-body and owner profile inspection return bodies. Explicit peer-isolation test: another agent sees the binding in roster/bootstrap/register inbox events, never the template body. A body/binding digest mismatch on explicit recovery read/save never writes a replacement file. Verify --save resolves only the authenticated agent's snapshot location and rejects escape/cross-agent destinations.
- Retry IDs preserve one identity/result. Persistence survives reopening and agent rename; role remains independent.
- Recovery accepts a matching own snapshot, restores matching shipped content if absent, and detects changed/missing content without silently switching. Test the real helper used by the skill, not a duplicate algorithm.
- UI None default, explicit selection submission, escaped profile title/body and connect guidance. Human double-click profile shows exact bound text and accurate snapshot state, including a matching old snapshot after package drift, absent snapshot with matching package, mismatch/corrupt/unreadable snapshot, unavailable old content and untemplated agents. Verify owner-only authorization, confinement and bounded reads; no arbitrary memory exposure, peer body delivery, all-profile prefetch or snapshot mutation by viewing.
- Agent config disclosure: test toggle state, accessible expanded state and persistence across polling/pane changes without lost drafts; manually or in a real browser verify flush geometry and no chat bleed at top/middle/bottom scroll positions, expanded/collapsed states and narrow/desktop widths. Include the shared human profile and other room layouts as regression checks. A DOM/string test alone cannot establish visual correctness; report any missing browser evidence.
- Installer copies the catalog and all selected resources; installed launcher can perform explicit selected-body retrieval.
Run relevant Python and UI suites with existing ResourceWarning discipline. Add tests for actual contract boundaries, not prose/heading snapshots.

Behavior:
Review the template wording for distinct emphasis, explicit opt-in, preserved task scope, honest findings and brevity. Check the shipped-body 3,072-byte bound. Remove repeated base-skill instructions and filler; a reader should identify the unique behavior from the profile text without reading this design plan. Exercise small realistic examples, including a sound change that every reviewer may approve, a regression for defensive review, a questionable assumption for adversarial review, a narrow fix tempting adjacent refactors for conservative engineering, and genuinely different approaches under a negotiable premise for creative design. Report these as behavioral observations, not a guarantee of model behavior. Peer review can perform this within the authorized review workflow; do not create unrelated agents or live side effects.
